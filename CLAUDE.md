# Правила работы для Claude в этом проекте

## Git: коммиты

- После каждого законченного логического изменения (фича, фикс, рефакторинг, конфиг) — предлагай закоммитить: покажи краткое summary изменений и предлагаемый текст коммита, дождись подтверждения ("да" / "да, но поправь текст" / "нет").
- Не смешивай в одном коммите разные по смыслу изменения. Если diff затрагивает разное — предложи разбить на несколько коммитов.
- Формат сообщений: `feat: ...`, `fix: ...`, `refactor: ...`, `docs: ...`, `chore: ...`, `test: ...` — коротко, на русском после двоеточия.
- Не делай `git push` без явного запроса в конкретный момент.
- Если просят "закоммить всё как есть" — всё равно кратко покажи, что именно коммитится, перед выполнением.

## Git: версии (теги)

- Веди CHANGELOG.md: при каждом коммите добавляй строку в раздел `## [Unreleased]` с сутью изменения.
- Периодически — когда накопилось несколько feat/fix, или пользователь подтвердил рабочую точку как стабильную — предлагай поставить git tag по semver (`MAJOR.MINOR.PATCH`):
  - PATCH — багфикс, поведение не изменилось
  - MINOR — новая функциональность, обратно совместимая
  - MAJOR — breaking change (сломан формат данных/API/интерфейс)
  - Объясняй, почему именно эта версия и какая цифра растёт.
- При простановке тега: перенеси содержимое `## [Unreleased]` в CHANGELOG.md под номер версии и дату, оставь `## [Unreleased]` пустым.
- Не создавай тег без подтверждения пользователя.

## Безопасность

- Никогда не коммить `.env`, ключи, токены, пароли, файлы из `.gitignore`. Если что-то похожее попало в diff — остановись, предупреди, не коммить автоматически.
- Секреты и конфиги-примеры держи в `.env.example` с пустыми плейсхолдерами, реальные значения — только в `.env` (в gitignore).

## Логирование

- В проекте обязательно должно быть логирование в файл (папка `logs/`, добавь в `.gitignore`), а не только вывод в консоль.
- Логируй: старт/завершение выполнения, ключевые шаги обработки, все ошибки и исключения с полным traceback, входные параметры при сбое (без секретов).
- Используй уровни (DEBUG/INFO/WARNING/ERROR), не print/console.log в проде.
- Формат записи: время — уровень — модуль/функция — сообщение, чтобы по логу можно было понять, что и где сломалось, без чтения кода.
- Если пишешь скрипт/парсер, который может частично упасть на части данных (например, при парсинге списка вакансий) — логируй каждую проблемную единицу отдельно (что именно и почему не обработалось), не только финальный traceback.
- При добавлении нового модуля — сразу подключай логгер, не оставляй "на потом".
- Ротация логов (по размеру/дате), если проект долгоживущий — чтобы папка `logs/` не разрослась бесконтрольно.

## Notion: ежедневный лог

- Claude Code сам не пишет в Notion — он готовит текст, который пользователь (или Claude в чате) заносит в таблицу "Ежедневный лог проекта".
- В конце рабочей сессии (или по запросу "дай отчёт за день") — сформируй сводку в этом формате:
  ```
  Дата: ГГГГ-ММ-ДД
  Коммиты: <краткий список за сегодня, через "; ">
  Теги/версии: <если ставился тег — какой и почему; иначе "—">
  Заметки: <проблемы/решения/что осталось на завтра>
  ```
- Эту сводку пользователь вставляет строкой в базу "Ежедневный лог проекта" в Notion (или просит Claude в чате Claude.ai сделать это через Notion-интеграцию).

## Структура и гигиена проекта

- Если создаёшь новые модули/скрипты — соблюдай уже заданную структуру папок проекта, не сваливай файлы в корень.
- Обновляй README.md, если меняется способ запуска, зависимости или структура проекта.
- Обновляй `requirements.txt` / `package.json` / `pyproject.toml` при добавлении новых зависимостей — в том же коммите, где зависимость впервые используется.

## Общение

- Изменения показывай кратко: что сделано, какие файлы затронуты — без длинных пересказов и вступлений.
- Если задача неоднозначна — короткий уточняющий вопрос вместо предположений.
